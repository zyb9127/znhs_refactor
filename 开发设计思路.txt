一、具体流程
 1、用户意图：推荐套餐

### 任务一：配置下发与配置同步稳定性优化（解决现网 Bug）

#### 核心问题背景
多实例 ES 配置读取 + Redis/Pub-Sub 同步链路存在不稳定情形：环境变量解析异常（分号前缀）、ES doc_type 不兼容、meta 指针缺失时回退本地文件等。

---

#### 验收标准（行为级）

| 编号 | 标准描述 | 验收方式 |
|---|---|---|
| S1-1 | 服务以任意合法 `environment` 值启动（含 `production_noauth`），启动日志无"无效运行环境"警告 | 查启动日志关键字 |
| S1-2 | 生产/灰度环境启动后，`[SkillLoader]` 日志中**不出现** `⚠️ 生产模式下所有技能包均来自本地文件` | 查运行日志 |
| S1-3 | SkillManager 列表在 ES 有数据时，页面技能包数量 ≥ ES 中已发布 `api_nodes` 的技能包数量 | 对比 Postman 查询结果与页面 |
| S1-4 | 单实例发布/修改配置后，**5 分钟内**（轮询间隔内）所有其他实例的 `skill_registry` 自动刷新到最新版本 | 多实例部署验证，查各实例日志 `[ConfigPoller] 检测到变更` |
| S1-5 | ES 节点临时不可用（任一节点下线）时，服务不崩溃，降级读 Redis 或本地文件，**响应码 200**，日志记录 WARNING 而非 ERROR | 摘除一个 ES 节点后压测 |
| S1-6 | 配置发布（Save）后立即调用 `/api/config-source` 诊断接口，`config_source` 显示 `es` 或 `redis`，不为 `local` | 接口验证 |

#### 量化指标

| 指标 | 目标值 | 测量方法 |
|---|---|---|
| 配置同步延迟（Redis Pub/Sub 正常时） | **< 3 秒** | 发布后 watch 各实例 `loaded_at` 变化时间差 |
| 配置同步延迟（仅轮询兜底时） | **≤ poll_interval_seconds（默认 300 秒）** | 关闭 Redis 后测量最大延迟 |
| ES 查询失败后服务可用率 | **100%**（降级不中断） | 注入故障后持续压测 60 分钟，success_rate = 接口成功数 / 总请求数 |
| 启动时 ES 连接成功率 | **≥ 99%**（3 节点任一可用即可） | 随机关停 1-2 节点时重启服务 10 次 |
| 配置发布成功率（ES 可用时） | **100%** | 连续发布 20 次，ES 写入全部成功 |

### 任务二：话术 Context 工程优化（入参→固定映射域→槽位关联匹配逻辑优化）

#### 核心问题背景
当前链路：接口出参 `response_extract` → `resource_context` 7 大固定域 → 话术模板 `linked_vars` 槽位消费。现存问题：槽位与域的关联规则不清晰，匹配逻辑存在空值穿透、优先级混乱等问题。

---

#### 验收标准（行为级）

| 编号 | 标准描述 | 验收方式 |
|---|---|---|
| S2-1 | 接口出参字段经 `response_extract` → 7 大固定域映射后，**无字段丢失**（配置了映射的字段全部出现在 `resource_context`） | 单元测试 / 日志验证 |
| S2-2 | 话术模板 `linked_vars` 中声明的槽位变量，**全部能从对应固定域中解析到值**（含多层 JSON Path 取值） | 构造标准测试用例验证 |
| S2-3 | 槽位值为 `None` / 空字符串时，话术生成**不报错**，按配置的默认值或占位符填充 | 构造空值测试用例 |
| S2-4 | 同一槽位变量在多个固定域中均有值时，**优先级规则明确可配置**（如 `user_info` > `domain_ext`），不出现随机覆盖 | 配置优先级后验证 |
| S2-5 | 7 大固定域名称和字段结构在 SkillManager 「数据流映射」Tab 中可视化展示，运营人员无需看代码即可理解映射关系 | 人工走查 UI |
| S2-6 | 修改槽位关联配置后，**不重启服务**即可生效（热重载 or 保存即生效） | 修改保存后直接调用推荐接口验证 |

#### 量化指标

| 指标 | 目标值 | 测量方法 |
|---|---|---|
| 槽位填充成功率（标准测试集） | **≥ 95%**（测试集 ≥ 20 条真实话术请求） | 跑自动化测试用例，统计槽位非空比例 |
| 空值穿透导致话术生成失败率 | **0%**（有默认值兜底） | 构造全量空值入参，验证服务正常返回 |
| 映射逻辑变更后热生效时间 | **< 10 秒** | 保存配置到下一条请求生效的时间差 |
| 话术模板匹配准确率（意图对应模板命中） | **≥ 90%**（标准测试集，含边界意图） | 构造 ≥ 30 条多意图测试用例，统计命中率 |
| 接口出参→固定域映射覆盖率 | **100%**（配置了映射规则的字段） | 核查配置 vs 实际 context 字段 |

## 一、逻辑不清晰的根本原因

当前 `SkillConfigEditor.vue` 的接口编辑弹窗存在一个根本性的认知负担：**"三步骤"和"7大标准域"是两个平行的概念体系，用户始终不知道自己在哪个层次操作，目标是什么**。

具体表现：
- 步骤①"配置请求" → 步骤②"模拟数据" → 步骤③"出参映射"，三步各自独立，看不到整体数据流向
- `response_extract` / `field_transform` 是技术术语，非技术运营人员看不懂
- "中间数据集"的概念没有可视化，用户填完②看不出对③有什么影响
- 7大标准域藏在"标准数据关联" Tab 下，和接口编辑弹窗是割裂的

## 二、具体优化方向

### 优化1：接口编辑弹窗改为"以输出为导向"的引导式布局

**现状**：三步是从配置视角（怎么调接口）出发设计的，用户搞不清楚最终会产出什么。

**建议**：把步骤顶部加一个"产出预览区"，始终保持可见，随用户填写实时更新：

```
┌─────────────────────────────────────────────────────────┐
│  产出结果（实时预览）                                       │
│  ┌─────────────────────────────────────────────────────┐│
│  │ ✓ current_package  ✓ usage  ✓ tags  ✗ user_info ... ││
│  │ 已覆盖 3/7 个标准域 · 被 2 个话术模板引用              ││
│  └─────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────┘
① 配置请求  ──  ② 出参映射（粘贴样例 + 定义映射规则）
```

产出区的 7 个标准域用"亮色=已配置 / 灰色=未配置"的 chip 显示，这样用户在任何步骤都能一眼知道"我的目标达到了没有"。

### 优化2：response_extract / field_transform 改用"领域语言"标注

**现状**：两个 JSON 文本框，看不出关系，也不知道填什么。

**建议**：在两个文本框上方加固定说明栏，并用箭头示意数据流：

```
接口响应 JSON
   │
   ▼  response_extract（第一步：取出中间数据块，给它们命名）
   │  例：{ "raw_tags": "bean.tags" }  ← 意思是把 bean.tags 取出来，叫做 raw_tags
   ▼
中间数据块（raw_tags, current_package, ...）
   │
   ▼  field_transform（第二步：决定每个中间块写入哪个标准域）
   │  例：usage ← raw_tags（只保留流量相关字段）
   ▼
7 大标准域（current_package / usage / tags / ...）
   │
   ▼  话术模板 linked_vars 消费
```

同时在 `response_extract` 文本框右侧加一个"从样例 JSON 快速提取"按钮，点击后自动解析样例 JSON 的顶层 key 并生成候选的 extract 规则，用户只需勾选需要的字段。

---

### 优化3：field_transform 从纯 JSON 改为"表格化配置"

**现状**：用户需要手写如下 JSON，难度高且容易出错：
```json
{
  "usage": { "from": "raw_tags", "type": "filter_include", "include_keys": ["近3月平均流量"] }
}
```

**建议**：增加一个"可视化配置模式"开关，用表格替代 JSON 手写：

| 标准域（写入哪里） | 来源数据块（from） | 映射方式 | 包含/排除字段 |
|---|---|---|---|
| usage ↓ | raw_tags ▼ | 只保留 ▼ | [近3月流量...] × [选择字段] |
| current_package ↓ | current_package ▼ | 整块透传 ▼ | — |
| tags ↓ | raw_tags ▼ | 排除 ▼ | [近3月流量...] × |

字段选择用 checkbox 列表，来源于 response_extract 的提取结果（已有数据），这样用户不需要记字段名，直接勾选。"高级 JSON 模式"保留给有经验的用户。

---

### 优化4：新建 Skill 流程与编辑 Skill 完全对齐

**现状**：新建 Skill（步骤创建模式）和编辑 Skill 弹窗是两套入口，共用同一个 `SkillConfigEditor`，但行为不完全一致（模式A有省份/意图直连后端，模式B是本地草稿），用户体感割裂。

**建议**：
1. 新建 Skill 第一步收集 省份 + 意图 后，**立即切换为和编辑完全一样的三 Tab 布局**（接口配置 / 标准数据关联 / 话术模板），而不是继续走独立的步骤表单
2. 新建时后端临时创建一个 draft 记录（省份+意图确定后即可），后续编辑逻辑完全复用已有代码

---

### 优化5：验证入口——在编辑弹窗内直接测试

**现状**：编辑完接口需要关闭弹窗，回到列表，点"测试"才能验证结果。

**建议**：在接口编辑弹窗的步骤②（出参映射）下方，增加一个"验证映射结果"内联面板：

```
─────────────────────────────────────────────────
验证映射结果
手机号 [15010470528____] 
附加参数 extra_data [________________]
[▶ 执行验证]   状态: ✅ 成功 · current_package ✓ usage ✓ tags ✓
─────────────────────────────────────────────────
```

点击后直接调用 `/api/dry-run-mapping` 接口（后端仅执行数据获取+映射，不生成话术），返回每个标准域的实际填充值，用户可以立刻确认映射是否正确，不需要离开当前弹窗。

---

### 优化6：7大标准域与话术模板的关联关系可视化

**现状**：数据流映射 Tab 的左右两栏（数据来源 / 话术模板）之间没有连线，用户看不出哪个域被哪个模板消费了。

**建议**：在"标准数据关联" Tab 中，点击某个标准域 chip（如 `usage`），右侧话术模板列表高亮展示所有引用了该域的模板，同时在模板行内显示具体的槽位变量名（如 `usage_line`）。反过来，点击某个话术模板，左侧高亮该模板依赖的所有标准域。这种双向高亮能让"接口→域→模板"的映射链路一目了然，无需看代码。
