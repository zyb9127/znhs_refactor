一、具体流程
 1、用户意图：推荐套餐

### 任务一：配置下发与配置同步稳定性优化（解决现网 Bug）

#### 核心问题背景
多实例 ES 配置读取 + Redis/Pub-Sub 同步链路存在不稳定情形：环境变量解析异常（分号前缀）、ES doc_type 不兼容、meta 指针缺失时回退本地文件等。

---

#### 验收标准（行为级）

| 编号 | 标准描述 | 验收方式 |
|---|---|---|
| S1-1 | 服务以任意合法 `environment` 值启动（含 `production_noauth`），启动日志无"无效运行环境"警告 | 查启动日志关键字 |
| S1-2 | 生产/灰度环境启动后，`[SkillLoader]` 日志中**不出现** `⚠️ 生产模式下所有技能包均来自本地文件` | 查运行日志 |
| S1-3 | SkillManager 列表在 ES 有数据时，页面技能包数量 ≥ ES 中已发布 `api_nodes` 的技能包数量 | 对比 Postman 查询结果与页面 |
| S1-4 | 单实例发布/修改配置后，**5 分钟内**（轮询间隔内）所有其他实例的 `skill_registry` 自动刷新到最新版本 | 多实例部署验证，查各实例日志 `[ConfigPoller] 检测到变更` |
| S1-5 | ES 节点临时不可用（任一节点下线）时，服务不崩溃，降级读 Redis 或本地文件，**响应码 200**，日志记录 WARNING 而非 ERROR | 摘除一个 ES 节点后压测 |
| S1-6 | 配置发布（Save）后立即调用 `/api/config-source` 诊断接口，`config_source` 显示 `es` 或 `redis`，不为 `local` | 接口验证 |

#### 量化指标

| 指标 | 目标值 | 测量方法 |
|---|---|---|
| 配置同步延迟（Redis Pub/Sub 正常时） | **< 3 秒** | 发布后 watch 各实例 `loaded_at` 变化时间差 |
| 配置同步延迟（仅轮询兜底时） | **≤ poll_interval_seconds（默认 300 秒）** | 关闭 Redis 后测量最大延迟 |
| ES 查询失败后服务可用率 | **100%**（降级不中断） | 注入故障后持续压测 60 分钟，success_rate = 接口成功数 / 总请求数 |
| 启动时 ES 连接成功率 | **≥ 99%**（3 节点任一可用即可） | 随机关停 1-2 节点时重启服务 10 次 |
| 配置发布成功率（ES 可用时） | **100%** | 连续发布 20 次，ES 写入全部成功 |

### 任务二：话术 Context 工程优化（入参→固定映射域→槽位关联匹配逻辑优化）

#### 核心问题背景
当前链路：接口出参 `response_extract` → `resource_context` 7 大固定域 → 话术模板 `linked_vars` 槽位消费。现存问题：槽位与域的关联规则不清晰，匹配逻辑存在空值穿透、优先级混乱等问题。

---

#### 验收标准（行为级）

| 编号 | 标准描述 | 验收方式 |
|---|---|---|
| S2-1 | 接口出参字段经 `response_extract` → 7 大固定域映射后，**无字段丢失**（配置了映射的字段全部出现在 `resource_context`） | 单元测试 / 日志验证 |
| S2-2 | 话术模板 `linked_vars` 中声明的槽位变量，**全部能从对应固定域中解析到值**（含多层 JSON Path 取值） | 构造标准测试用例验证 |
| S2-3 | 槽位值为 `None` / 空字符串时，话术生成**不报错**，按配置的默认值或占位符填充 | 构造空值测试用例 |
| S2-4 | 同一槽位变量在多个固定域中均有值时，**优先级规则明确可配置**（如 `user_info` > `domain_ext`），不出现随机覆盖 | 配置优先级后验证 |
| S2-5 | 7 大固定域名称和字段结构在 SkillManager 「数据流映射」Tab 中可视化展示，运营人员无需看代码即可理解映射关系 | 人工走查 UI |
| S2-6 | 修改槽位关联配置后，**不重启服务**即可生效（热重载 or 保存即生效） | 修改保存后直接调用推荐接口验证 |

#### 量化指标

| 指标 | 目标值 | 测量方法 |
|---|---|---|
| 槽位填充成功率（标准测试集） | **≥ 95%**（测试集 ≥ 20 条真实话术请求） | 跑自动化测试用例，统计槽位非空比例 |
| 空值穿透导致话术生成失败率 | **0%**（有默认值兜底） | 构造全量空值入参，验证服务正常返回 |
| 映射逻辑变更后热生效时间 | **< 10 秒** | 保存配置到下一条请求生效的时间差 |
| 话术模板匹配准确率（意图对应模板命中） | **≥ 90%**（标准测试集，含边界意图） | 构造 ≥ 30 条多意图测试用例，统计命中率 |
| 接口出参→固定域映射覆盖率 | **100%**（配置了映射规则的字段） | 核查配置 vs 实际 context 字段 |

## 一、逻辑不清晰的根本原因

当前 `SkillConfigEditor.vue` 的接口编辑弹窗存在一个根本性的认知负担：**"三步骤"和"7大标准域"是两个平行的概念体系，用户始终不知道自己在哪个层次操作，目标是什么**。

具体表现：
- 步骤①"配置请求" → 步骤②"模拟数据" → 步骤③"出参映射"，三步各自独立，看不到整体数据流向
- `response_extract` / `field_transform` 是技术术语，非技术运营人员看不懂
- "中间数据集"的概念没有可视化，用户填完②看不出对③有什么影响
- 7大标准域藏在"标准数据关联" Tab 下，和接口编辑弹窗是割裂的

## 二、具体优化方向

### 优化1：接口编辑弹窗改为"以输出为导向"的引导式布局

**现状**：三步是从配置视角（怎么调接口）出发设计的，用户搞不清楚最终会产出什么。

**建议**：把步骤顶部加一个"产出预览区"，始终保持可见，随用户填写实时更新：

```
┌─────────────────────────────────────────────────────────┐
│  产出结果（实时预览）                                       │
│  ┌─────────────────────────────────────────────────────┐│
│  │ ✓ current_package  ✓ usage  ✓ tags  ✗ user_info ... ││
│  │ 已覆盖 3/7 个标准域 · 被 2 个话术模板引用              ││
│  └─────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────┘
① 配置请求  ──  ② 出参映射（粘贴样例 + 定义映射规则）
```

产出区的 7 个标准域用"亮色=已配置 / 灰色=未配置"的 chip 显示，这样用户在任何步骤都能一眼知道"我的目标达到了没有"。

### 优化2：response_extract / field_transform 改用"领域语言"标注

**现状**：两个 JSON 文本框，看不出关系，也不知道填什么。

**建议**：在两个文本框上方加固定说明栏，并用箭头示意数据流：

```
接口响应 JSON
   │
   ▼  response_extract（第一步：取出中间数据块，给它们命名）
   │  例：{ "raw_tags": "bean.tags" }  ← 意思是把 bean.tags 取出来，叫做 raw_tags
   ▼
中间数据块（raw_tags, current_package, ...）
   │
   ▼  field_transform（第二步：决定每个中间块写入哪个标准域）
   │  例：usage ← raw_tags（只保留流量相关字段）
   ▼
7 大标准域（current_package / usage / tags / ...）
   │
   ▼  话术模板 linked_vars 消费
```

同时在 `response_extract` 文本框右侧加一个"从样例 JSON 快速提取"按钮，点击后自动解析样例 JSON 的顶层 key 并生成候选的 extract 规则，用户只需勾选需要的字段。

---

### 优化3：field_transform 从纯 JSON 改为"表格化配置"

**现状**：用户需要手写如下 JSON，难度高且容易出错：
```json
{
  "usage": { "from": "raw_tags", "type": "filter_include", "include_keys": ["近3月平均流量"] }
}
```

**建议**：增加一个"可视化配置模式"开关，用表格替代 JSON 手写：

| 标准域（写入哪里） | 来源数据块（from） | 映射方式 | 包含/排除字段 |
|---|---|---|---|
| usage ↓ | raw_tags ▼ | 只保留 ▼ | [近3月流量...] × [选择字段] |
| current_package ↓ | current_package ▼ | 整块透传 ▼ | — |
| tags ↓ | raw_tags ▼ | 排除 ▼ | [近3月流量...] × |

字段选择用 checkbox 列表，来源于 response_extract 的提取结果（已有数据），这样用户不需要记字段名，直接勾选。"高级 JSON 模式"保留给有经验的用户。

---

### 优化4：新建 Skill 流程与编辑 Skill 完全对齐

**现状**：新建 Skill（步骤创建模式）和编辑 Skill 弹窗是两套入口，共用同一个 `SkillConfigEditor`，但行为不完全一致（模式A有省份/意图直连后端，模式B是本地草稿），用户体感割裂。

**建议**：
1. 新建 Skill 第一步收集 省份 + 意图 后，**立即切换为和编辑完全一样的三 Tab 布局**（接口配置 / 标准数据关联 / 话术模板），而不是继续走独立的步骤表单
2. 新建时后端临时创建一个 draft 记录（省份+意图确定后即可），后续编辑逻辑完全复用已有代码

---

### 优化5：验证入口——在编辑弹窗内直接测试

**现状**：编辑完接口需要关闭弹窗，回到列表，点"测试"才能验证结果。

**建议**：在接口编辑弹窗的步骤②（出参映射）下方，增加一个"验证映射结果"内联面板：

```
─────────────────────────────────────────────────
验证映射结果
手机号 [15010470528____] 
附加参数 extra_data [________________]
[▶ 执行验证]   状态: ✅ 成功 · current_package ✓ usage ✓ tags ✓
─────────────────────────────────────────────────
```

点击后直接调用 `/api/dry-run-mapping` 接口（后端仅执行数据获取+映射，不生成话术），返回每个标准域的实际填充值，用户可以立刻确认映射是否正确，不需要离开当前弹窗。

---

### 优化6：7大标准域与话术模板的关联关系可视化

**现状**：数据流映射 Tab 的左右两栏（数据来源 / 话术模板）之间没有连线，用户看不出哪个域被哪个模板消费了。

**建议**：在"标准数据关联" Tab 中，点击某个标准域 chip（如 `usage`），右侧话术模板列表高亮展示所有引用了该域的模板，同时在模板行内显示具体的槽位变量名（如 `usage_line`）。反过来，点击某个话术模板，左侧高亮该模板依赖的所有标准域。这种双向高亮能让"接口→域→模板"的映射链路一目了然，无需看代码。

【实现】空槽位口径开关 biz_config.slot_fallback

⚠️ 本节记录的是初版设计（默认 drop、山东按技能包开占位符）。默认口径已在下一节
「口径反转：默认从『删句』改为『照实透传填槽』」中整体翻转，零值口径也一并翻转。
本节保留作为问题根因与三层改造思路的说明，读默认值/零值口径请以下一节为准。

配置项（技能包级，前端「模板匹配与填槽设置 → 高级设置 → 兜底也取不到值时，这个槽位怎么办」可配）：
  {"mode": "passthrough|drop", "placeholder": "**", "treat_as_empty": ["**", ...]}
  - mode=passthrough：现默认值，保留整句、槽位处填占位符（默认 **），总部与分中心模板槽位对称。
    （初版名为 placeholder，仍作历史别名接受。）
  - mode=drop：旧行为，槽位取不到值就删掉整句；现需显式落库才生效。
  - treat_as_empty：入参中视为「没取到值」的掩码值；passthrough 未显式配置时默认为占位符自身。

改造前的问题不是「不支持填 **」，而是**两条路径不对称**（山东反馈的根因）：
  - 字段不传 → 三层都在删：prompt_builder 空值 continue 不进上下文、生成规则第 2 条要求删整句、
    script_step._strip_residual_placeholders 再删含占位符的子句；
  - 分中心传字面 ** → 被当成有效事实，既进【上下文数据】（出现「月均消费：**」脏事实行），
    又被确定性填槽填回话术。
  故 placeholder 模式先把掩码值归一成「缺失」（_drop_masked_values + 各取值点 _unmask），
  让「传 **」与「不传」收敛到同一条路径，再统一决定呈现方式。

三层改动：
  1. engine/prompt_builder.py：normalize_slot_fallback / _drop_masked_values；掩码值不入上下文；
     缺失事实文案与生成规则按模式切换。掩码只比标量整值，正文里含星号的描述不受影响；
     extra_info/extra_context 整包 JSON 兜底行同样过滤，否则对称性会被这行破坏。
  2. prompt/script_generation.py：规则拆成片段，drop/placeholder 复用同一批防编造/防串填条文，
     只替换「空槽位怎么办」及第 3、4 条对它的交叉引用（SCRIPT_GEN_RULES 拼装结果与拆分前逐字节一致）。
  3. steps/script_step.py：_fill_residual_placeholders 作为确定性兜底，模型没填的 {槽位} 换成 **
     而非删子句；有映射事实的槽位仍优先填真值。

两个口径边界（有意为之）：
  - 值确实是 0（0元/0分钟/0GB）仍按原口径略过整句，不填 **：零值是真事实，写成 ** 会诱导坐席补错数字。
    【已废止】下一节把零值改为照实填 0（仍是真事实，但改为原样播报而非略过）；此口径现仅存于 drop 模式。
  - 某些分中心宁可不说：在**那条模板自己的「话术要求」**里写提示词（如「月均消费、流量无数据时
    不要提这两句，直接讲推荐产品」），规则第 2 条显式让位于【话术要求】（与字数规则让位于
    【话术要求】的既有约定一致）。略过范围由话术要求自述，可为一句/连续几句/一整段。
    因 script_requirement 是模板级字段，而各分中心各自维护自己的模板行，故同省不同分中心
    对同一槽位可以有相反口径，无需再加省下一级的配置维度。
    注意这条覆盖是**提示词级**（模型遵从），不像全局开关那样确定性：模型万一没删句、把占位符
    留在了输出里，层3 仍会填成 **。这是有意的降级方向——填 ** 比把 {avg_consume} 播给客户安全。

预览一致性：/api/templates/preview_prompt 读取该技能包的 slot_fallback，避免运营在预览里
看到「删句」而线上是填占位符。

【实现】口径反转：默认从「删句」改为「照实透传填槽」
──────────────────────────────────────────────────────────────────────
上一轮的实现是「默认删句、山东按技能包开占位符开关」，本轮按上述要求整体反转为
平台默认照实填槽，且零值口径同时翻转。核心思路：平台只负责忠实填槽，不替业务判断
「这句该不该说」；要个性化省略，由那条模板自己的【话术要求】表达。

一、默认口径（mode=passthrough，无需任何配置，全省生效）
  入参 **   → 输出 **      （掩码归一成「无事实」，再由占位符兜底填回 **）
  入参 空   → 输出 **      （与传 ** 走同一条路径，产出逐字节一致）
  入参 0    → 输出 0       （0 是真事实，照实播报「0元」「0GB」）
  一律不删句：保留模板原句结构，总部与分中心各自人工维护的模板槽位始终对称，
  坐席照读不会漏项或解释错位。

二、与上一轮实现的差异（本轮改动点）
  1. 默认值翻转：normalize_slot_fallback 缺省 mode 由 drop 改为 passthrough，
     缺省 treat_as_empty 由空集改为 {占位符}，即所有省份默认都做掩码归一。
  2. 零值口径翻转（关键）：上一轮两种模式下零值都「略过整句」，理由是写成 ** 会诱导
     坐席补错数字；本轮改为照实填 0。默认规则里原有的「严禁说出 0元/0分钟/0个月/0GB」
     负向约束已移除（留在 drop 口径里），否则会与「照实说 0」自相矛盾。
     ⚠️ 生产风险：模板若写成「含{pkg_voice}分钟通话」，语音为 0 时会播报「含0分钟通话」；
     「优惠{n}个月」为 0 时会播报「优惠0个月」。这类句子须由运营在该模板的【话术要求】里
     写明省略规则（见第四点），或该省整体回退 drop。
  3. mode 命名：canonical 名由 placeholder 改为 passthrough（覆盖了「0 照实填」语义）；
     placeholder 作为历史别名继续接受，已落库的配置不会失效。
  4. 模式常量下沉到 prompt/script_generation.py（最底层、无依赖），engine/prompt_builder.py
     再导出 SLOT_FALLBACK_PLACEHOLDER 别名，避免规则正文与模式判定两处分叉。
  5. build_gen_rules / build_missing_facts_tail 签名由 (placeholder) 改为 (mode, placeholder)
     —— 原来用「placeholder 为空串」表示 drop，默认翻转后这个约定会反直觉。
     SCRIPT_GEN_RULES 现在等于 build_gen_rules() 的结果（= passthrough 正文）。

三、三层落点（与上一轮相同，只是默认分支互换）
  层1 prompt_builder：掩码值在六处取值点 + extra_info/extra_context/passthrough 整包
      兜底行上一律归一成空，使「传 **」与「不传」完全等价；规则正文与【缺失事实】
      结尾按 mode 选择。
  层2 script_generation：规则片段化，只有「取不到值 / 值为 0 时怎么办」随 mode 变化，
      防编造、防串填、模板为主体框架等条文共用一份（测试断言两种口径复用同一批片段）。
  层3 script_step._post_process：默认把残留占位符换成 **（保句），drop 才删子句。
      这是确定性兜底 —— 模型即使没听规则第 2 条把句子删了，这里也只能救回它留下的
      占位符，故层2 与层3 的口径必须同步切换。

四、个性化省略：写在该模板的【话术要求】里
  规则第 2 条显式让位：「若下方【话术要求】明确指出某项无数据（或为 0）时不要提及，
  则该项以【话术要求】为准，按其所述范围整体略过（可为一句、连续几句或一整段）」。
  例：「月均消费、流量无数据或为 0 时不要提这两句，直接讲推荐产品」。
  因此同省不同分中心的模板可以有相反口径，无需为此改技能包配置。

五、回退开关（mode=drop）：后端保留，前端不暴露
  用途：某省话术已按旧口径调优过、或上线后发现「0分钟」类表述不可接受时，按技能包
  快速回滚，不必改代码发版。设置方式 PUT /api/skills/{province}/{intent}/biz_config
  写入 {"slot_fallback": {"mode": "drop"}}，或经技能包导入带入。

  为什么不放在话术编辑页面（原「兜底也取不到值时，这个槽位怎么办」面板已删除）：
  1. 三个控件对运营都不是可决策项 —— 翻转后 passthrough 对所有省都正确，drop 只是工程
     回退杆；占位符山东要的就是 **，且改它会连带变成默认掩码（运营无法预期的副作用）；
     treat_as_empty 是上游入参质量规则，与话术无关。
  2. 粒度错配且有误伤：该配置是**技能包级**的，运营编辑一条模板却会改掉该省所有模板的
     行为。而运营真正的诉求「这句没数据时别说」是**模板级**的，已由该模板自己的
     script_requirement 承载（规则第 2 条显式让位），粒度才对得上。

零、需求拆解与「做/不做」的判断
  天津这一条需求里混了四种能力，泛化价值差别很大，逐条判断而不是整体上：
    ① 数组按条件选元素（userinfo_json 按 timeType 取账期）→ 做。账期/分类数组会反复出现。
    ② 数值计算（套餐外上网费 + 套餐外通话费）           → 做。
    ③ 条件分档选话术（和 <1 元推场景一，否则场景二）      → 做，且**必须确定性**：
       两个场景推的是不同产品（5G安心月包-1元 / -3元，业务编码不同），
       选错是业务错误而不是措辞问题，不能交给模型判断。
    ④「说哪个月」（{XX}月）                              → **不做成配置**。
       把 4 个账期都按标签注入，「挑哪个月最值得说」是软判断，LLM 擅长，
       写在话术要求里即可；数值仍来自确定性注入的事实行，精度不受影响。
       为它建 argmax 配置属于过度设计。

一、原有能力边界（做之前先确认差距，避免重复造）
  - 取值：DataStep._get_path 只支持点路径取标量，**遇到 list 直接返回 None**；
    response_extract / field_transform 无 JSONPath、无数组下标、无按条件筛选数组元素。
  - 计算：只有 unit_convert（单字段单位换算）与 field_rename，**没有任何算术/比较**。
    PackageDiff 有差值计算，但语义死绑「当前套餐 vs 当前推荐条」，不能算任意两入参字段。
  - 数组进提示词：透传字段里的数组会被 _fmt_passthrough_value 转成**整包紧凑 JSON**，
    既不结构化也没法精确填槽。
  - 子字段占位符 {域[子键]}：_subfield_roots **只注册 dict**，顶层 list 不注册，
    所以 {userinfo_json[...]} 这类占位符运行时一律落空。
  - 模板匹配：静态字符串标签（product_id/stage/scene）+ 12 档降级链，
    **无法表达任何数值条件**。

  另发现一个坑（已由本次能力绕开）：若在 passthrough_fields 里配 userinfo_json.over_flow，
  代码因 userinfo_json 是 list 而把它塞进 product_field_allow，而那个白名单只服务
  products/recommended_packages —— 这条配置会**静默失效**，不报错也不生效。

二、架构选择：加「派生字段」层，不给模板选择加规则引擎
  最容易走错的一步是在 template 上加 match_rules/when 做条件选模板 —— 那要连带改
  template_selector 的 12 档、template_index 的桶键、conflict_detector 的冲突分组、
  schema、前端与一批测试，且引入第二套匹配语义。
  改为：**只新增派生字段计算层，产出普通槽位，让现有各条消费路径原样吃它**。
    - 话术里 {派生名} / {派生名[子键]} 直接引用；
    - biz_config.template_match.*_from 本就是「从哪个字段取值」，可直接消费派生字段，
      于是**零改动复用完整 12 档匹配**。
  关键收益：array_find 返回**整个元素 dict**，而 dict 型透传值会被 build_prompt 注册为
  子字段根 —— 于是 {当月资源} 与 {当月资源[over_flow_fee]} 同时可用，
  正好绕开「顶层 list 不注册为子字段根」的既有限制，**没改 prompt_builder 一行**。

三、后端实现（plugins/derived_fields.py，新增；steps/data_step.py 接入）
  配置位置：api_nodes.<节点>.derived_fields，**仅 direct_mode=passthrough 生效**
  （营销助手模式即走这条链路）。按声明顺序求值，后面的规则可引用前面已算出的派生名。
  三个算子（受限声明式，**不做表达式 DSL、不用 eval** —— 前端才能表单化、运营才看得懂，
  也不引入注入风险与「配置即代码」的调试难题）：
    array_find  {"type":"array_find","from":"userinfo_json","where":{"timeType":"0"}}
                → 返回第一个全条件命中的元素（整个 dict）；where 按字符串比，兼容 "0" 与 0
    sum         {"type":"sum","from":["当月资源.over_flow_fee","当月资源.over_voice_fee"]}
    bucket      {"type":"bucket","from":"超套费用合计",
                 "rules":[{"lt":1,"value":"场景一"},{"value":"场景二"}]}
                 多字段条件写法：{"when":{"路径":{"ne":0},"路径2":{"eq":0}},"value":"…"}
  取值路径：新写了一个解析器（**没动 _get_path**，避免影响 response_extract 的既有行为），
  根名先查已算出的派生字段再查原始报文，支持 dict 键与 list 数字下标。
  比较算子只有 lt/lte/gt/gte/eq/ne —— 够表达阈值分档与零值判定，不扩成通用表达式。

  ★ 三条「不臆造」语义（都有单测锁定，是本次最容易做错的地方）：
    1. sum 全部路径取不到 → 返回 None 而**不是 0**。否则「没数据」会被分档当成真的 0，
       天津规则 3 会把用户错误路由到场景一（推错产品）。
    2. 比较算子遇到空值一律判否，不拿 None 当 0 比。
       所以「上网费为空」不会被 {"ne":0} 误判成「非零」而误触发账单异常提示。
    3. bucket 声明了 from 却取不到值 → **整条不产出，不落兜底档**。
       落兜底等于没有依据就选了一档。纯 when 写法（不声明 from）不受此限，
       兜底档正常生效，配 "value":"" 即表示「不追加」（值为空的派生字段不注入）。
  健壮性：未知 type / 单条求值异常只告警跳过，不影响其余字段与整体话术
  —— 派生字段是增强项，不该让话术整体失败。
  防污染：派生名与 7 大标准域同名时跳过并告警（标准域只走 resources 通道）；
  与透传入参同名时以派生配置为准（显式配置意图优先）并告警。

四、与 slot_fallback 新默认口径的联动（正好咬合，不是巧合）
  天津报文里 over_flow / over_voice 是字符串 "0"，其余资源字段大量是空串。
  上一轮把默认口径翻成「照实填充、0 填 0」，恰好是天津规则 2 的前提 ——
  {超额量} 必须显示成 0，才可能触发「费用≠0 但超额量=0 → 提示坐席结合账单解释」。
  若还是旧的 drop 口径，这句会被整句删掉，规则 2 根本无从触发。
  空串仍按 ** 处理，两者语义不混。

五、前端实现（SkillConfigEditor.vue，接口配置弹窗「出参/透传」页 ③ 段）
  沿用 field_transform 的既有范式（不引入新交互风格）：**表格配置优先 + 高级 JSON 兜底**，
  ifcEditForm.derived_fields（JSON 串）是唯一数据源，dfRows 只是它的可视投影。
  - 三种算子各自的子表单：array_find（数组 + 多条 key=value 选取条件）、
    sum（多路径 multiple select）、bucket（判断依据 + 档位行：算子/阈值/取值，兜底档一项）。
  - from/路径候选来自样例解析出的透传字段 + 前面已定义的派生名（支持层层引用）。
  - 表格表达不了的写法（多字段 when 条件）整条标记「高级规则」并**原样保留在 row.raw**，
    否则运营点开一次弹窗就会把这类配置擦掉。
  - 保存前校验 validateDerivedFields：只挡「一定跑不出结果」的写法（type 不支持、
    必填路径为空、bucket 无档位、**兜底档放在中间导致后面档位永远取不到**、与标准域同名）。
  持久化四处同步（openIfcEdit 加载 / 快照变更检测 / saveIfcEdit body / saveLocalIfcEdit +
  emitChange）。Mode A 后端按节点 merge（body 没有的键保留原值），所以清空要显式传 {}。

  ★ 顺手修掉一个既有 bug（Mode B / Import 路径）：
    emitChange 原先不显式序列化 request_variant，它只靠 _extra 透传；而
    saveLocalIfcEdit 把 _extra 整个从**编辑前的旧节点**拷过来，_extra 展开又在最后 ——
    结果在创建/导入页改「接口规范」（标准 ↔ 营销助手）会被旧值盖回去，静默保存不上。
    修法：把 request_variant 与 derived_fields 都提为一等字段（从 _extra 排除名单里剔除、
    load 时单独取、emitChange 显式写出、saveLocalIfcEdit 保存前把 _extra 里的同名残留删掉）。
    天津是营销助手模式，这个 bug 会直接卡住配置，故一并修。

  问题：三个算子（array_find/sum/bucket）平铺成一个类型下拉，运营要先理解算子名才知道

  改法：
    - 分两组呈现，落库仍是同一个 derived_fields 对象：
        ① 字段计算（array_find / sum）—— 取值、算数，产出**数据值**
        ② 逻辑判断（bucket）      —— 比条件，产出**结论**
      两组用左侧色条 + 徽标区分；逻辑判断组不再有类型下拉（类型固定 bucket）。
    - 落库顺序 = 界面顺序（字段计算全部 → 逻辑判断全部，组内相对顺序原样保留）。
      后端按声明顺序求值、判断依赖计算结果，该顺序即所见即所得。
      （反向依赖不成立：array_find 需要 list、sum 需要数值，都不可能消费 bucket 的标签串。）
    - bucket 的每条规则显式选「模式」，取代原先用运算符空值表达兜底：
        比大小（threshold）/ 多字段条件（when）/ 兜底（fallback）

    - 「判断依据」(from) 改为**仅在存在「比大小」规则时才显示/校验**：纯 when 的判断
      没有单一依据。commit 时 from 为空不再写 "from": ""。
    - 仍保留高级 JSON 兜底：同一路径挂多个运算符等表格放不下的写法整条保原样，不擦除。

问题一：山东话术每次生成完全相同（连标点都不变）
  根因（三因叠加，温度为主因）：
  1) 生成温度被硬编码为 0.3 —— steps/script_step.py `_generate_llm` 两处
     temperature=0.3，且 generate() 显式传参会覆盖 agents_config.json 的 0.7，
     故生产实际温度=0.3，接近贪婪解码 → 同一入参必得同一 token 序列。
  2) 提示词约束过强 —— shandong/套餐推荐 biz_config 的 script_requirement 要求
     "方括号数值原样保留、严禁改写"，模型基本在复述模板。
  3) 确定性填槽 —— _apply_slot_facts/_post_process 按入参精确填槽，数据部分本就固定。
  修复：
  - 采样温度改为可配置，默认 0.8（新增 _DEFAULT_SCRIPT_TEMPERATURE），
    优先读 biz_config.strategy.script_temperature，非法/缺省回退 0.8；
    _generate_llm 改用 self._script_temperature（不再硬编码 0.3）。
  - 保留确定性填槽 → 数值仍准确，仅表达/标点产生变化。
  - 如需按省调稳/调活，配 strategy.script_temperature 即可（无需改代码）。
  - 前端已支持可视化配置：技能配置页「话术模板」Tab → 顶部「话术生成参数」面板，
    滑块/数字框调「采样温度」（0~1.5，默认 0.8）与「话术字数上限」，点「保存设置」
    写回 biz_config.strategy（SkillConfigEditor.vue，创建/导入/管理三种保存路径均已带上）。

【问题与修复 · 2026-08-31】更新服务后页面查不到 ES 配置
────────────────────────────────────────────────────────
现象：更新服务后，智能话术配置管理页显示「暂无智能话术配置」，之前发布到 ES 的配置读不到。

根因：es_config_store.py 全程使用 elasticsearch-py 7.x 的调用风格
      （http_auth / body= / doc_type= / ignore=，共约 25 处）。这些在 8.x 起被移除或改名
      （http_auth→basic_auth、body→显式 kwargs、doc_type 删除、ignore→ignore_status），
      且 8.x 客户端默认拒绝连接非 8.x 服务端。线上一旦装到 8.x/9.x，官方客户端不可用 →
      ES 初始化/读写全失败 → 页面「暂无配置」。（数据仍在 ES，未丢，只是客户端连不上。）

修复（代码层面自适应，无需变更部署环境）：
  在 es_config_store.py 增加「ES 客户端版本兼容层」：
  1) _lib_major()：识别已安装 elasticsearch-py 主版本（兼容 __version__ 为元组/字符串）。
  2) _build_client()：
     - <=7.x  → 官方客户端，既有生产行为完全不变（零回归）；
     - 未装 / >=8.x → 自动切换内置 REST 适配器，并打 WARNING 说明原因。
  3) _RestEsClient（基于 httpx，httpx 已是既有依赖）：直连 ES HTTP 接口，
     对外保持与 7.x 完全一致的签名与响应结构，因此 25 个调用点一行都不用改。
     - 支持 info / index / get / update / delete / search / indices.{create,get_mapping,put_settings}
     - doc_type 兼容：带 type 走 /{index}/{type}/{id}（5.x/6.x），不带走 /{index}/_doc/{id}（7.x+）
     - update 路径按版本区分：7.x+ /{index}/_update/{id}，5.x/6.x /{index}/{type}/{id}/_update
     - ignore 语义与 es-py 对齐：命中状态码返回响应体，否则抛 _EsHttpError
     - 文档 _id（形如 tianjin:营销活动:biz_config:1）整段百分号编码，避免被当路径分隔符致 404
     - 多节点顺序故障转移；服务端已应答的错误不再重试；全部不可达抛 ConnectionError
  4) requirements.txt 不再锁定 elasticsearch 大版本（兼容层已消除版本敏感性）。

【问题与修复 · 2026-09-07】山东"换一换"话术无变化（提示词写太死）

现象：切入/挽留等短话术点"换一换"重生成，字数与内容都不变；灵运平台调高采样温度后仍无变化。

根因：基础提示词（prompt/script_generation.py · SCRIPT_GEN_RULES）第 4 条把模板锁成
      "模板正文就是骨架，必须沿用它的句子顺序、段落结构与表达方式，逐句保留……不得改写成
      自己的行文、不得调整句序"——等于要求模型逐字复述模板。叠加确定性填槽，模型几乎没有
      发挥空间，温度再高 token 序列也基本不变。第 2 条缺失槽位分支、缺失事实块里也有
      "不得改写句式/不得调整句序"的措辞锁。此外前端默认【话术要求】(DEFAULT_SCRIPT_REQ)
      写"只做占位符填充和语句通顺化"，作为最高优先级 rule 6 进一步压制泛化。

修复（既保事实准确、又给表达泛化）：
  1) 第 4 条改为「以话术模板为内容蓝本、用自己的自然口语重新表达」：
     - 模板界定要覆盖的环节/卖点/事实/大致顺序 → 必须逐一覆盖、不遗漏也不新增；
     - 但不再逐字复述，允许更换措辞/句式/连接词/语气、并可适度调整句序 → 每次生成有合理差异；
     - 明确「槽位事实值（数字/金额/套餐名/方括号数值）须严格照第 2、3 条原样填入、不得改动」，
       可变的只是事实之外的行文表达（数字准确性由第 2、3 条保证，与泛化不冲突）。
  2) 第 2 条缺失槽位分支、缺失事实块 TAIL 去掉"不得改写句式/不得调整句序"措辞锁，
     只保留"不得删句/不得丢信息点/保留 <PH>/不得编造数值顶替"这些事实性约束。
  3) 前端 DEFAULT_SCRIPT_REQ（SkillConfigEditor.vue / TemplateEditDialog.vue /
     TemplateConfig/index.vue 三处）同步：由"只做占位符填充和语句通顺化"改为"覆盖每个要点、
     不增删卖点，但用自己的口语重新表达、每次有合理差异；事实数值照实填不改动"。

注意：
  - 山东线上已保存的模板各自带 script_requirement（rule 6，最高优先级）。若其中仍写"严禁改写/
    照模板逐字"之类，会继续压制泛化——需在配置页把该模板话术要求也放开（仅锁数值、放开行文）；
    DEFAULT_SCRIPT_REQ 改动只影响之后新建/重置的模板。
  - "方括号数值原样保留"这类要求只锁数字，与放开行文不冲突，可保留。
  - 灵运平台"换一换"若自身按入参做了结果缓存，需其侧关缓存或带随机因子，否则同参仍返回同结果。
